# 작업계획서 — 콕배정 (물류센터 하역장 배정 서비스)

내부 참고용 문서. 제출물이 아니며, `기능명세서.md`·`설계_참고자료.md`·`콕배정-API.yml`·`콕배정-DB.dbml`·개발 컨벤션(3일 일정)을 근거로 실행 단위 태스크로 쪼갠 것이다.

## 0. 전제

- 기간: 2026-09-08 ~ 2026-09-10 (3일)
- 스택: Vue 3 + Vite(frontend) / Spring Boot 3.5.13, Gradle, Java 21(backend) / PostgreSQL / Spring AI(OpenAI, gpt-4o-mini)
- 배포: Railway 통합 배포 (backend, frontend, PostgreSQL 플러그인)
- 인프라 스캐폴딩은 완료된 상태에서 시작 (`backend/`, `frontend/`, `docker-compose.yml` — 로컬 기동 검증 완료)
- Should 우선순위인 Epic 4(AI 요약)는 시간 부족 시 가장 먼저 제외

## 1. Day 1 — DB 스키마 + 백엔드 기본 골격

목표: 엔티티/레포지토리가 갖춰지고, 창고·도크 등록/수정 API가 동작하는 상태.

### 1-1. DB 스키마 반영
- [ ] `warehouse`, `dock`, `assignment`, `admin` 4개 Entity 작성 (`콕배정-DB.dbml` 기준, enum은 Java enum으로 매핑)
- [ ] `assignment(dock_id, status='ACTIVE')` 부분 유니크 인덱스 마이그레이션 반영 (DBML 표기 한계로 별도 DDL 필요 — REQ-NFR-004)
- [ ] Repository 인터페이스 4종 작성

### 1-2. 공통 에러 처리 골격 (설계_참고자료.md §2 기준, 이후 모든 API가 의존)
- [ ] `ErrorCode` enum (코드/HTTP상태/기본메시지)
- [ ] `BusinessException`
- [ ] `GlobalExceptionHandler` (`@RestControllerAdvice`)
- [ ] `ErrorResponse` DTO

### 1-3. 관리자 인증 (REQ-FUNC-005)
- [ ] `admin` 비밀번호 BCrypt 해시 저장/검증 (spring-security-crypto)
- [ ] JWT 발급/검증 유틸 (jjwt) — `/admin/**` 전용 필터, 방문 기사 API는 무인증
- [ ] `POST /admin/login` → `TokenResponse`, 실패 시 `AUTH_FAILED`(401)

### 1-4. 창고 관리 CRUD (REQ-FUNC-006)
- [ ] `POST/PUT /admin/warehouses`, `/admin/warehouses/{id}`
- [ ] `/admin/warehouses/{id}/(de)activate` (소프트 딜리트, `deleted_at`)
- [ ] `WarehouseCreateRequest/UpdateRequest`, `WarehouseAdminResponse` DTO + `@NotBlank` 검증

### 1-5. 도크 관리 CRUD (REQ-FUNC-007)
- [ ] `POST/PUT /admin/docks`, `/admin/docks/{id}`
- [ ] `/admin/docks/{id}/deactivate` — ACTIVE 배정 존재 시 `DOCK_HAS_ACTIVE_ASSIGNMENT`(400)로 차단
- [ ] `DockCreateRequest/UpdateRequest`(소속 창고 변경 불가), `DockAdminResponse` DTO

**Day 1 완료 기준**: 위 API들이 Postman/curl로 정상 요청·에러 응답(404/400/401) 모두 확인됨, 빌드 통과.

## 2. Day 2 — 배정 핵심 로직 + 프론트 배정 화면

목표: 방문 기사가 QR/링크로 들어와 실제로 도크를 배정받고 취소할 수 있는 흐름 완성 (서비스 핵심 가치).

### 2-1. 방문 기사 조회 API
- [ ] `GET /warehouses/{id}` — 비활성 창고는 `WAREHOUSE_NOT_FOUND`(404)
- [ ] `GET /warehouses/{id}/docks` — 비활성 도크(`deleted_at NOT NULL`) 제외, REQ-NFR-001(2초 이내 응답)

### 2-2. 도크 배정 (REQ-FUNC-003, REQ-NFR-004)
- [ ] `POST /assignments` — `AssignmentCreateRequest`(dockId, driverName, scheduledTime, pin) 검증
- [ ] PIN 해시 저장 (평문 금지, REQ-NFR-002)
- [ ] 동시 배정 충돌을 DB 유니크 제약 위반 → `ASSIGNMENT_CONFLICT`(409)로 변환
- [ ] 비활성 창고 배정 시도 → `WAREHOUSE_INACTIVE`(403)
- [ ] AVAILABLE 아닌 도크 배정 시도 → `DOCK_NOT_AVAILABLE`(400)

### 2-3. 배정 취소 (REQ-FUNC-004)
- [ ] `POST /assignments/{id}/cancel` — PIN 검증 실패 시 `PIN_MISMATCH`(401)
- [ ] 이미 취소된 배정 재취소 시 `ALREADY_CANCELLED`(400)

### 2-4. Vue 배정 화면 (SCR-ASSIGN-001/002)
- [ ] `/w/:warehouseId` 진입 시 창고명 + 도크 목록(규격/상태/특성 배지) 렌더링
- [ ] 도크 선택 → 배정 폼(이름/시간/PIN) → 성공/실패(409 충돌 메시지 포함) 처리
- [ ] 배정 완료 후 취소 화면(PIN 입력) 연결
- [ ] 모바일 반응형 확인 (REQ-NFR-003)
- [ ] 조회 실패 시 재시도 안내 UI (REQ-NFR-005)

**Day 2 완료 기준**: 같은 도크에 동시 요청 2건 보내면 하나는 201, 하나는 409 — 수동으로 직접 재현해서 확인.

## 3. Day 3 — 관리자 화면 + AI 요약 + 통합 테스트 + 배포

### 3-1. 관리자 화면
- [ ] 관리자 로그인 화면 → JWT를 로컬 스토리지에 저장, 이후 요청에 `Authorization` 헤더 부착
- [ ] 창고/도크 목록 + 등록/수정/비활성화 UI

### 3-2. 창고 혼잡도 요약 (REQ-FUNC-008, Should — 시간 부족 시 최우선 제외)
- [ ] `GET /admin/warehouses/{id}/summary` — Service 계층에서 도크/배정 데이터 집계 후 OpenAI 호출, 응답 문장 그대로 반환 (별도 저장 없음)
- [ ] 도크가 하나도 없는 창고 조회 시 기본 문구 반환 (LLM 호출 스킵)
- [ ] `WarehouseSummaryResponse`(warehouseId, occupancyRate, summary) 프론트 렌더링

### 3-3. 수동 테스트 시나리오 전체 실행 (개발 컨벤션 문서 표 그대로)
- [ ] 동시 배정 충돌 → 201/409
- [ ] PIN 불일치 → 401 PIN_MISMATCH
- [ ] 비활성 창고 신규 배정 차단 → 403 WAREHOUSE_INACTIVE
- [ ] ACTIVE 배정 있는 도크 비활성화 차단 → 400 DOCK_HAS_ACTIVE_ASSIGNMENT
- [ ] 비활성 도크 노출 여부 → 목록에서 제외
- [ ] AI 요약 데이터 없음 → 기본 문구

### 3-4. Railway 배포
- [ ] Railway 프로젝트 생성, PostgreSQL 플러그인 추가
- [ ] backend 서비스 연결 + 환경변수(`SPRING_DATASOURCE_*`, `OPENAI_API_KEY`, `JWT_SECRET`) 등록
- [ ] backend 배포 URL 확인 후 frontend 서비스 `VITE_API_BASE_URL` 빌드 환경변수로 등록, 재배포
- [ ] CORS 설정 (프론트/백엔드 도메인 분리이므로 필수)
- [ ] 배포된 URL로 REQ-FUNC-001~008 전체 스모크 테스트

**Day 3 완료 기준**: 배포된 URL에서 QR 진입 → 배정 → 취소, 관리자 로그인 → 도크 비활성화까지 실제로 동작.

## 4. 완료 정의 (Definition of Done, 원문 그대로)

- 관련 API가 API 설계서의 요청/응답 스펙과 정확히 일치한다
- 에러코드가 실제 해당 예외 상황에서 발생한다 (수동 트리거해 확인)
- 빌드가 깨지지 않는다
- 로컬에서 실제 요청을 보내 정상 응답을 눈으로 확인했다
- 요구사항_정의서에 명시된 예외 케이스가 하나도 빠지지 않았다

시간이 부족하면 다음 순서로 뺀다 (Should > 부가 기능 > 필수 기능 순으로 보호):
