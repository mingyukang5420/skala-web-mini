# 후속 작업

리뷰나 작업 중 발견했지만 지금 당장 블로킹은 아닌 항목을 기록하는 문서. 항목마다 출처(PR/이슈), 내용, 지금 블로킹이 아닌 이유를 남긴다.

- 내용: 현재 백엔드에 Checkstyle/Spotless 등 린터/포매터가 설정되어 있지 않음.
- 블로킹 아닌 이유: 3일짜리 프로젝트의 첫 백엔드 PR(13개 파일) 단계라 컨벤션 드리프트보다 남은 필수 기능(인증/CRUD/배정 로직) 구현 속도가 더 중요함. 코드 스타일이 자리잡기 전에 룰을 확정하는 것도 리스크. Day 1 후반부까지 코드량이 늘어난 뒤 재검토 예정.

## PR #14 / 이슈 #1 - id 필드 타입 불일치 (DBML int vs Java Long)

- 내용: `콕배정-DB.dbml`에서는 각 테이블의 `id`가 `int`로 정의되어 있으나, JPA 엔티티에서는 `Long`으로 매핑됨.
- 블로킹 아닌 이유: 이 프로젝트 규모(3일 미니 프로젝트, 소규모 데이터)에서는 실질적인 문제가 없음. 참고로만 남김.

## PR #18 / 이슈 #5 - 필수 쿼리 파라미터 누락 시 응답이 앱 공통 에러 포맷을 따르지 않음

- 내용: `GET /admin/docks`는 `warehouseId`를 `@RequestParam Long warehouseId`(기본값 없음)로 필수 처리한다. 이 파라미터를 생략하고 요청하면 Spring이 `MethodArgumentNotValidException`이 아닌 `MissingServletRequestParameterException`을 던지는데, `GlobalExceptionHandler`가 이 예외를 처리하지 않아 `{code, message}` 형태가 아닌 Spring 기본 whitelabel 에러 바디(`{timestamp, status, error, path}`)가 그대로 노출됨. 상태 코드(400) 자체는 맞음 - 직접 재현해 확인.
- 블로킹 아닌 이유: `콕배정-API.yml`에도 이 케이스에 대한 응답 스펙이 명시되어 있지 않고, 상태 코드는 400으로 올바르며, 지금까지의 관리자 API 중 필수 쿼리 파라미터가 있는 첫 사례라 기존 코드에서 이미 반복되던 문제도 아님. 프론트가 관리자 화면에서 이 경로를 항상 `warehouseId`와 함께 호출하도록 구현하면 실사용에서는 도달하기 어려운 경로. 다음에 필수 쿼리 파라미터를 쓰는 엔드포인트가 추가될 때 `GlobalExceptionHandler`에 `MissingServletRequestParameterException` 핸들러를 함께 추가하는 것을 권장.

## PR #19 / 이슈 #6 - `{id}` 경로 변수에 숫자가 아닌 값이 오면 응답이 앱 공통 에러 포맷을 따르지 않음

- 내용: `GET /warehouses/{id}`, `GET /warehouses/{id}/docks`는 `@PathVariable Long id`로 받는다. `id`에 `abc`처럼 숫자로 파싱할 수 없는 값을 넣으면 Spring이 `MethodArgumentTypeMismatchException`을 던지는데, `GlobalExceptionHandler`가 이 예외를 처리하지 않아 `{code, message}` 형태가 아닌 Spring 기본 whitelabel 에러 바디(`{timestamp, status, error, path}`)가 그대로 노출됨. 상태 코드(400) 자체는 맞음 - 직접 재현해 확인(`GET /warehouses/abc` -> 400, whitelabel 바디).
- PR #18에서 로그된 `MissingServletRequestParameterException` 미처리와 같은 패턴(원인 예외 타입만 다름)이며, 관리자 API뿐 아니라 무인증 방문 기사 API에서도 동일하게 재현되어 두 번째 사례로 확인됨.
- 블로킹 아닌 이유: `콕배정-API.yml`에도 이 케이스에 대한 응답 스펙이 명시되어 있지 않고 상태 코드는 400으로 올바름. 방문 기사는 QR/링크로 진입해 `id`를 직접 손으로 입력하지 않으므로 실사용에서 도달하기 어려운 경로. 두 번째 사례가 확인된 만큼, 다음에 경로 변수를 받는 엔드포인트를 추가하기 전에 `GlobalExceptionHandler`에 `MethodArgumentTypeMismatchException`(및 `MissingServletRequestParameterException`)을 한 번에 처리하는 공통 핸들러 추가를 권장.

## PR #20 / 이슈 #7 - `dock.status`가 배정 생성 시 자동으로 OCCUPIED로 전환되지 않음

- 내용: `AssignmentService.create()`는 `assignment(dock_id, status='ACTIVE')` 부분 유니크 인덱스로만 동시 배정을 막고, `dock.status` 컬럼 자체는 건드리지 않는다. 따라서 배정이 생성된 이후에도 `GET /warehouses/{id}/docks` 응답에서 해당 도크의 `status`는 여전히 `AVAILABLE`로 조회된다.
- 근거: `설계_v2`(`02_설계_DB`)의 "사용자 결정 사항"에 "도크 상태 갱신 방식: 자동 반영 없음. 배정 실패(409) 응답 수신 시에만 '다른 기사가 먼저 배정했습니다. 새로고침 후 다시 시도해주세요' 안내로 처리"라는 명시적 결정이 있어, 이번 PR의 구현은 이 결정과 일치한다. `콕배정-DB.dbml`/`기능명세서.md`/`설계_참고자료.md`/`콕배정-API.yml` 어디에도 배정 시 `dock.status`를 전환한다는 요구사항은 없다.
- 블로킹 아닌 이유: 문서상 명시적 근거(설계_v2)가 있어 현재 구현이 기획 의도와 일치하는 것으로 판단됨. 다만 이 동작은 Day 2 Vue 배정 화면(SCR-ASSIGN-001) 구현 시 "도크 목록에서 이미 배정된 도크가 시각적으로 AVAILABLE로 계속 보이는" 사용자 경험으로 이어질 수 있어, 프론트 작업 착수 전 사람이 한 번 더 확인하는 것을 권장.

## PR #21 / 이슈 #8 - 존재하지 않는 assignment id로 취소 요청 시 401 PIN_MISMATCH 처리 (404 아님)

- 내용: `AssignmentService.cancel(id, request)`는 `assignmentRepository.findById(id)`가 비어있을 때 별도의 NOT_FOUND 계열 에러 대신 `PIN_MISMATCH`(401)를 던진다. 즉 존재하지 않는 배정 id와 PIN이 틀린 경우를 클라이언트 입장에서 구분할 수 없다.
- 근거: `콕배정-API.yml`의 `/assignments/{id}/cancel`은 200/400/401만 정의하고 404가 없다. `설계_참고자료.md`와 `02_설계_DB`의 `설계_v3`/`설계_v4`(둘 다 상태: 확정) 에러코드 표에서도 이 엔드포인트에는 PIN_MISMATCH/ALREADY_CANCELLED만 있고 NOT_FOUND 계열이 없다 - 같은 문서에서 창고/도크 엔드포인트는 WAREHOUSE_NOT_FOUND/DOCK_NOT_FOUND를 명시적으로 갖고 있는 것과 대비되어 의도된 설계로 보인다. PR #20에서 존재하지 않는 dockId를 DOCK_NOT_AVAILABLE(400)로 처리한 것과 같은 패턴이며, v1~v5 전체를 확인했으나 반박 근거는 발견되지 않았다.
- 블로킹 아닌 이유: 문서상 명시적으로 이 판단을 반박하는 근거는 없고, 존재 여부를 노출하지 않는 편이 PIN 기반 무인증 취소 흐름의 보안 관점에서도 더 타당하다. 다만 PR #20의 dock 사례처럼 기획자가 명시적으로 결정한 문장(예: "사용자 결정 사항")이 발견된 것은 아니고 문서의 침묵/생략 패턴에 근거한 추론이므로, 프론트 취소 화면(SCR-ASSIGN-002) 구현 시 "없는 배정 id"에 대한 UX 문구가 "PIN이 틀렸습니다"로 노출되어도 괜찮은지 사람이 한 번 더 확인하는 것을 권장. -> PR #22 검증 결과 실제로 이 문구 그대로 노출됨을 확인, 별도 이슈 없음.

## PR #22 / 이슈 #9 - CORS 전용 이슈가 원래 13개 이슈 목록(#1~#13)에 없었던 기획 단계 누락

- 내용: `설계_참고자료.md`(아키텍처 설계)에 "프론트/백엔드 도메인 분리로 CORS 설정 필요"라고 명시돼 있었음에도, 지금까지 어떤 이슈에도 CORS 설정 작업이 포함되어 있지 않았다. PR #22(Vue 배정 화면 구현) 작업 중 dev server(5173)에서 백엔드(8080)로 직접 요청하는 실제 브라우저 테스트를 하다가 처음 발견됨.
- 이 PR에 함께 포함시킨 것에 대한 판단: 직접 로컬 테스트로 발견됐고, 다른 작업을 블로킹하지 않으며, Vue 배정 화면 자체가 CORS 설정 없이는 동작할 수 없는 밀접한 관계라 이번 PR에 함께 넣는 것이 타당하다고 판단(별도 PR/이슈로 분리할 정도의 독립적 작업은 아니었음).
- 블로킹 아닌 이유: 이미 이번 PR에서 구현/검증까지 완료됐으므로 지금 시점에 블로킹은 아님. 다만 애초에 기획 단계(#1~#13 이슈 목록)에서 CORS가 별도 이슈로 잡히지 않았던 것은 계획 누락이므로, 회고 시 "설계 문서에 있는데 이슈로 안 잡힌 항목이 더 있는지" 재점검하는 차원에서 회고성 이슈 등록을 검토할 가치가 있음.

## PR #22 / 이슈 #9 - `CorsConfig`의 `allowedMethods`에 미사용 `DELETE` 포함

- 내용: `CorsConfig.addCorsMappings()`가 `allowedMethods("GET", "POST", "PUT", "DELETE")`를 설정하나, `콕배정-API.yml` 전체를 확인한 결과 `DELETE`를 사용하는 엔드포인트는 하나도 없음(관리자 창고/도크 비활성화도 전부 `POST /admin/.../deactivate` 형태).
- 블로킹 아닌 이유: 허용 메서드 목록에 미사용 메서드가 하나 더 있다고 해서 보안/기능상 위험이 생기지는 않음(실제 엔드포인트가 없으면 어차피 404). 사소한 코드 정리 대상으로만 기록.

## PR #23 / 이슈 #10 - 관리자 수정 폼의 비동기 초기값 로드가 사용자 입력을 덮어쓸 수 있는 레이스 컨디션

- 내용: `AdminWarehouseFormView.vue`/`AdminDockFormView.vue`는 `onMounted(loadExisting)`에서 기존 값을 비동기로 조회해 `name`/`form` ref에 대입한다. 이 조회가 사용자의 입력보다 늦게 완료되면(느린 네트워크 등) 사용자가 이미 수정 중이던 입력값이 조회 결과로 조용히 되돌아갈 수 있다. Playwright로 자동화된 매우 빠른 입력(필드 채움 직후 즉시 다음 동작)에서 실제로 한 번 재현됨. 로컬 환경(응답 지연 수십ms 미만)에서는 이후 재시도들에서 재현되지 않았다.
- 블로킹 아닌 이유: 실제 사람이 폼 진입 즉시(응답이 오기 전) 타이핑을 시작해 완료하는 시나리오는 로컬/일반적인 네트워크 환경에서는 발생 확률이 매우 낮음. 다만 Railway 등 원격 배포 환경은 왕복 지연이 커질 수 있으므로, 로딩 완료 전 폼 비활성화(`disabled`) 또는 로딩 스피너로 입력을 막는 방어적 UX를 다음 관리자 화면 개선 작업에서 검토 권장.
