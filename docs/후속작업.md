- 내용: `콕배정-DB.dbml`에서는 각 테이블의 `id`가 `int`로 정의되어 있으나, JPA 엔티티에서는 `Long`으로 매핑됨.

## PR #18 / 이슈 #5 - 필수 쿼리 파라미터 누락 시 응답이 앱 공통 에러 포맷을 따르지 않음

- 내용: `GET /admin/docks`는 `warehouseId`를 `@RequestParam Long warehouseId`(기본값 없음)로 필수 처리한다. 이 파라미터를 생략하고 요청하면 Spring이 `MethodArgumentNotValidException`이 아닌 `MissingServletRequestParameterException`을 던지는데, `GlobalExceptionHandler`가 이 예외를 처리하지 않아 `{code, message}` 형태가 아닌 Spring 기본 whitelabel 에러 바디(`{timestamp, status, error, path}`)가 그대로 노출됨. 상태 코드(400) 자체는 맞음 - 직접 재현해 확인.
- 블로킹 아닌 이유: `콕배정-API.yml`에도 이 케이스에 대한 응답 스펙이 명시되어 있지 않고, 상태 코드는 400으로 올바르며, 지금까지의 관리자 API 중 필수 쿼리 파라미터가 있는 첫 사례라 기존 코드에서 이미 반복되던 문제도 아님. 프론트가 관리자 화면에서 이 경로를 항상 `warehouseId`와 함께 호출하도록 구현하면 실사용에서는 도달하기 어려운 경로. 다음에 필수 쿼리 파라미터를 쓰는 엔드포인트가 추가될 때 `GlobalExceptionHandler`에 `MissingServletRequestParameterException` 핸들러를 함께 추가하는 것을 권장.

## PR #19 / 이슈 #6 - `{id}` 경로 변수에 숫자가 아닌 값이 오면 응답이 앱 공통 에러 포맷을 따르지 않음

- 내용: `GET /warehouses/{id}`, `GET /warehouses/{id}/docks`는 `@PathVariable Long id`로 받는다. `id`에 `abc`처럼 숫자로 파싱할 수 없는 값을 넣으면 Spring이 `MethodArgumentTypeMismatchException`을 던지는데, `GlobalExceptionHandler`가 이 예외를 처리하지 않아 `{code, message}` 형태가 아닌 Spring 기본 whitelabel 에러 바디(`{timestamp, status, error, path}`)가 그대로 노출됨. 상태 코드(400) 자체는 맞음 - 직접 재현해 확인(`GET /warehouses/abc` -> 400, whitelabel 바디).
- PR #18에서 로그된 `MissingServletRequestParameterException` 미처리와 같은 패턴(원인 예외 타입만 다름)이며, 관리자 API뿐 아니라 무인증 방문 기사 API에서도 동일하게 재현되어 두 번째 사례로 확인됨.
- 블로킹 아닌 이유: `콕배정-API.yml`에도 이 케이스에 대한 응답 스펙이 명시되어 있지 않고 상태 코드는 400으로 올바름. 방문 기사는 QR/링크로 진입해 `id`를 직접 손으로 입력하지 않으므로 실사용에서 도달하기 어려운 경로. 두 번째 사례가 확인된 만큼, 다음에 경로 변수를 받는 엔드포인트를 추가하기 전에 `GlobalExceptionHandler`에 `MethodArgumentTypeMismatchException`(및 `MissingServletRequestParameterException`)을 한 번에 처리하는 공통 핸들러 추가를 권장.

- 블로킹 아닌 이유: 문서상 명시적 근거(설계_v2)가 있어 현재 구현이 기획 의도와 일치하는 것으로 판단됨. 다만 이 동작은 Day 2 Vue 배정 화면(SCR-ASSIGN-001) 구현 시 "도크 목록에서 이미 배정된 도크가 시각적으로 AVAILABLE로 계속 보이는" 사용자 경험으로 이어질 수 있어, 프론트 작업 착수 전 사람이 한 번 더 확인하는 것을 권장.

## PR #21 / 이슈 #8 - 존재하지 않는 assignment id로 취소 요청 시 401 PIN_MISMATCH 처리 (404 아님)

- 근거: `콕배정-API.yml`의 `/assignments/{id}/cancel`은 200/400/401만 정의하고 404가 없다. `설계_참고자료.md`와 `02_설계_DB`의 `설계_v3`/`설계_v4`(둘 다 상태: 확정) 에러코드 표에서도 이 엔드포인트에는 PIN_MISMATCH/ALREADY_CANCELLED만 있고 NOT_FOUND 계열이 없다 - 같은 문서에서 창고/도크 엔드포인트는 WAREHOUSE_NOT_FOUND/DOCK_NOT_FOUND를 명시적으로 갖고 있는 것과 대비되어 의도된 설계로 보인다. PR #20에서 존재하지 않는 dockId를 DOCK_NOT_AVAILABLE(400)로 처리한 것과 같은 패턴이며, v1~v5 전체를 확인했으나 반박 근거는 발견되지 않았다.
- 블로킹 아닌 이유: 문서상 명시적으로 이 판단을 반박하는 근거는 없고, 존재 여부를 노출하지 않는 편이 PIN 기반 무인증 취소 흐름의 보안 관점에서도 더 타당하다. 다만 PR #20의 dock 사례처럼 기획자가 명시적으로 결정한 문장(예: "사용자 결정 사항")이 발견된 것은 아니고 문서의 침묵/생략 패턴에 근거한 추론이므로, 프론트 취소 화면(SCR-ASSIGN-002) 구현 시 "없는 배정 id"에 대한 UX 문구가 "PIN이 틀렸습니다"로 노출되어도 괜찮은지 사람이 한 번 더 확인하는 것을 권장. -> PR #22 검증 결과 실제로 이 문구 그대로 노출됨을 확인, 별도 이슈 없음.

## PR #24 / 이슈 #11 - 실제 OPENAI_API_KEY로 정상 호출 경로 사전 검증 필요 (데모/발표 전 필수)

- 내용: `WarehouseSummaryService.generateSummary()`는 `chatClient.prompt().user(prompt).call().content()`가 실패하면 집계값 기반 문장으로 폴백한다. 이 리뷰를 포함해 지금까지 이 개발 환경에는 실제 `OPENAI_API_KEY`가 없어(`sk-dummy` 더미 키만 사용) LLM이 실제로 자연어 요약을 생성해 반환하는 "정상 호출 경로"는 한 번도 검증되지 못했고, 검증된 것은 전부 폴백 경로다.
- 확인해야 할 것(사람이 실제 키로 직접 수행):
  1. `OPENAI_API_KEY` 환경변수에 유효한 OpenAI API 키를 설정(`backend/src/main/resources/application.yml`의 `spring.ai.openai.api-key: ${OPENAI_API_KEY}`, 모델은 `spring.ai.openai.chat.options.model: gpt-4o-mini`로 고정되어 있음 - 해당 계정에 `gpt-4o-mini` 접근 권한이 있는지도 함께 확인).
  2. 도크 2개 이상/일부 배정된 창고로 `GET /admin/warehouses/{id}/summary` 호출.
  3. **정상 응답과 폴백 응답을 구분하는 기준**: 폴백 문장은 정확히 `"전체 활성 도크 %d개 중 %d개가 배정되어 점유율은 %.0f%%입니다."` 형식의 기계적 문장(코드에 하드코딩됨, `WarehouseSummaryService.java`)이다. 실제 LLM이 응답하면 이 고정 템플릿과 다른, 더 자연스러운 문장(문장 구조/어휘가 매번 달라짐)이 와야 한다. 응답 시간도 참고 가능 - 이번 리뷰에서 더미 키로도 실패 전 네트워크 시도에 ~650ms가 걸렸으므로, 정상 키로는 이보다 다소 길거나 비슷한 시간이 걸리되 폴백 문장이 아닌 다른 문장이 오는지로 판별.
  4. 위 확인이 안 된 상태로 데모/발표에 들어가면, 키가 만료됐거나 권한이 없거나 네트워크가 막힌 경우에도 화면은 (의도된 대로) 폴백 문장으로 조용히 대체되어 "AI 요약이 실제로 동작하는지" 발표 중에는 구분할 수 없다는 점을 발표자가 인지하고 있어야 함.
- 블로킹 아닌 이유: 개발 환경에 실제 키가 없는 것은 이 프로젝트의 환경 제약이지 코드 결함이 아니며, 이 한계는 PR 본문에 정직하게 공개되어 있고 폴백 경로 자체는 이번 리뷰에서 5가지 시나리오 전부 직접 재현해 정상 동작을 확인했다. 다만 "실제 AI 요약이 살아있는 기능"이라는 것을 아무도 육안으로 확인하지 못한 채 데모에 들어가는 리스크가 있으므로, 발표 전 반드시 사람이 위 절차로 한 번 확인할 것을 강하게 권장.

## PR #24 / 이슈 #11 - LLM 호출 실패 시 `RuntimeException` 캐치 범위가 넓음

- 내용: `WarehouseSummaryService.generateSummary()`가 `chatClient.prompt().user(prompt).call().content()` 호출 전체를 `catch (RuntimeException e)`로 감싸 집계값 기반 문장으로 폴백한다. 이렇게 하면 진짜 외부 API 장애/네트워크 문제뿐 아니라, 예를 들어 프롬프트 구성 과정에서 생긴 코드 버그(NPE, IllegalArgumentException 등)까지 전부 "AI 응답 실패"로 조용히 삼켜져 폴백 문장으로 넘어가므로, 실제 버그가 있어도 겉으로는 정상 동작처럼 보일 수 있다.
- 근거: 이 프로젝트가 쓰는 `spring-ai-retry:1.1.4`(`backend/build.gradle`의 `springAiVersion=1.1.4`) jar를 직접 열어 확인한 결과 `org.springframework.ai.retry.TransientAiException`(재시도 가능한 일시적 오류)과 `NonTransientAiException`(재시도 불가능한 오류) 두 클래스가 있으나, 둘 다 `RuntimeException`을 직접 상속하고 공통 상위 타입(예: 별도의 `AiException` 계열)이 없다. 즉 "Spring AI 관련 예외만" 좁혀 잡으려면 `catch (TransientAiException | NonTransientAiException e)` 형태의 멀티캐치가 필요하다.
- 블로킹 아닌 이유: 이 메서드에서 실제로 프롬프트를 구성하는 값들(창고 이름, 도크/배정 개수)은 DB NOT NULL 제약과 이미 조회에 성공한 엔티티에서 나오므로, `chatClient` 호출 이전 단계에서 코드 버그로 예외가 날 가능성은 현재 구현상 낮음. 3일짜리 프로젝트 규모에서 지금 당장 멀티캐치로 좁히는 것보다 남은 작업이 우선이라 판단, 다음에 이 서비스를 수정할 기회(또는 별도 정리 작업)에 `TransientAiException | NonTransientAiException`으로 좁히는 것을 권장.

## PR #24 / 이슈 #11 - `WarehouseSummaryService.getSummary()`의 `existsByDockIdAndStatus` N+1 스타일 쿼리

- 내용: 창고의 점유율을 계산할 때 도크 목록을 조회한 뒤, 각 도크마다 `assignmentRepository.existsByDockIdAndStatus(dock.getId(), ACTIVE)`를 개별 호출한다(도크가 N개면 쿼리가 N+1번 나감).
- 블로킹 아닌 이유: 이 프로젝트 규모(창고 하나당 도크 수가 매우 적은 3일 미니 프로젝트)에서는 성능에 실질적 영향이 없다. 도크 수가 크게 늘어나는 시나리오가 생기면 배정 테이블을 `GROUP BY dock_id`로 한 번에 집계하는 쿼리로 교체하는 것을 권장하되, 지금은 참고용으로만 기록.

## PR #24 / 이슈 #11 - `WarehouseSummaryService`가 `WarehouseService`를 거치지 않고 별도로 창고를 조회함

- 내용: `WarehouseAdminController`는 `WarehouseService`와 `WarehouseSummaryService`를 함께 주입받는데, `WarehouseSummaryService.getSummary()`는 `WarehouseService.findWarehouseOrThrow()`(private)를 재사용하지 않고 `warehouseRepository.findById().orElseThrow(WAREHOUSE_NOT_FOUND)`를 자체적으로 다시 구현한다.
- 블로킹 아닌 이유: `WarehouseService`의 조회 메서드가 private이라 지금 구조에서 재사용하려면 package-private/public으로 바꾸는 리팩터링이 필요하고, 기존 코드베이스에서도 각 서비스가 자신의 리포지토리 조회를 독립적으로 갖는 패턴이 이미 자리잡고 있어 이번 PR만의 새로운 문제는 아니다. 창고 조회 로직 자체가 단순(`findById` + `WAREHOUSE_NOT_FOUND`)해 중복으로 인한 실질적 리스크는 낮음. 서비스 간 공용 조회 로직이 더 늘어나면 그때 공통화를 검토.
